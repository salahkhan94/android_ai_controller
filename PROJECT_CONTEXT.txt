PURPOSE
Build a Python AI application that observes and controls an Android emulator
running Hinge through Appium/ADB, using an LLM for written text prompts.
Current scope: text prompts only. Photo/image interpretation and photo-targeted
comments/likes are excluded. Phase 6 is cancelled at the user's request.
Screenshots remain available as UI diagnostic and verification evidence only.
The user runs Ubuntu 26.04 and has installed Genymotion, Appium, and ADB.

REQUESTED FEATURES
1. Profile comments and likes (first priority):
   - Read a profile's written prompt titles and responses.
   - Select a written prompt response as the comment target; never a photo.
   - Generate a very funny, perhaps slightly flirtatious, relevant comment.
   - Ultimately attach that comment to the selected item and send the like.
   - Phases 1–5 implemented. One explicitly authorized submission was attempted;
     the app advanced profiles without explicit confirmation. Do not retry it.
   - Current workflow: run.py handles one text profile end-to-end with mandatory
     per-comment terminal approval before preparation and submission. Phase 6 cancelled.
2. Conversations (later):
   - Open conversations with matches and detect new incoming messages.
   - Generate replies using the whole conversation so far as context.
   - Requires obtaining older messages, tracking observed history, and
     distinguishing incoming messages from already handled messages.

ARCHITECTURE DISCUSSED (RECOMMENDATIONS, NOT IMPLEMENTED)
Observe -> identify screen/extract content -> propose structured action ->
validate current state and target -> execute -> observe and verify result.
- Use Appium as the primary UI control interface; ADB for device diagnostics
  and management. Keep the currently working Genymotion environment.
- Prefer UI-tree text, IDs, accessibility labels, and bounds when available.
  Extract prompt content from XML. Retain screenshots for UI diagnostics and
  verification only; do not add photo analysis or image-targeted comments.
- Capture both sources close together and discard observations when the
  screen changes; they are not an atomic snapshot.
- Let the model select among extracted item IDs and propose text. Python
  validates and executes a small supported action set, not arbitrary code.
- Explicitly recognize profile, composer, and unexpected-screen states.
- Re-observe after navigation; avoid stale element handles and coordinates.
- Verify sends before any retry to prevent duplicate likes/comments.
- Review-before-send was proposed, but the user has not yet specified their
  preferred review policy versus unattended operation.
- Current scope is Phase 4 composer preparation and text entry; no sending is authorized.

PLAN: PROFILE PROMPT REPLIES FIRST
Phase 1 — Inspect the actual UI (read-only).
  Capture screenshot, XML, package/activity, and viewport dimensions from a
  visible profile. Inspect written prompts and their associated like buttons.
  Determine whether prompt titles, responses, and controls are exposed in XML.
  Do not assume selectors or layout before collecting these observations.
  Outcome: a documented extraction/control approach based on real UI evidence.

Phase 2 — Extract structured profile items.
  Introduce an observation/controller layer while keeping android_tester.py
  available as the connection smoke test.
  Represent each item with a local item ID, item type, prompt title, response
  text, and locator/bounds evidence tied to its observation.
  Use bounded scrolling and overlap deduplication if prompts span screens.
  Distinguish items from different profiles; stop if identity/state is unclear.
  Support written prompts only; photo crops and vision are out of scope.
  Outcome: a reliable list of candidate prompt targets from one profile.

Phase 3 — Generate and select comments without sending.
  Add a configurable model adapter; select provider/model when implementing.
  Give the model extracted prompt content, target IDs, and user tone settings.
  Request a few short, specific, funny, lightly flirtatious candidates and a
  preferred target/candidate. Avoid generic lines and invented personal facts.
  Treat profile text as untrusted content, not instructions to the agent.
  Validate output structure, target membership, nonempty text, and the actual
  app's comment length constraint once observed.
  Display selected prompt and candidate comments for user review.
  Outcome: useful grounded comments with no remote side effects.

Phase 4 — Connect a selected draft to the correct composer.
  Re-observe the same profile/item, open its like/comment composer, and confirm
  that the composer corresponds to the selected prompt before entering text.
  Make generation and submission separate operations; stop before submission
  until the user's desired sending/review policy is established.
  Outcome: the chosen draft is associated with the intended prompt reliably.

Phase 5 — Submit and verify when authorized.
  Recheck profile, target, and final text immediately before sending.
  Record attempted/confirmed/uncertain submission states locally.
  Verify the resulting UI; an ambiguous timeout must not trigger a blind retry.
  Stop on unexpected dialogs, profile changes, or missing controls.
  Outcome: one intended like/comment with evidence of success or clear uncertainty.

Phase 6 — CANCELLED: photo targets.
  User explicitly excluded image/photo interpretation and photo-targeted comments
  or likes. Do not implement this phase. Continue with written text prompts only.
